# Patterns — 2026-08-01

Session: debugging Expo SDK 57 crash in `npm-user-tracker-fresh` (drizzle-orm + expo-sqlite) on x86_64 emulator.

## Summary

- Root cause isolated: `react-native-reanimated`/`react-native-worklets` native runtime crashes Hermes V1 on x86_64 emulators (not app code).
- Proved via isolation: vanilla `create-expo-app` blank app + reanimated import = byte-identical crash; vanilla alone = stable.
- Verified full app + migrations on emulator by temporarily stubbing reanimated/worklets via metro `resolveRequest`.
- Migrations confirmed working (full schema rendered from live SQLite).

## Findings

### MISSING_INSTRUCTION
- Background long-running processes (metro dev server) started via `nohup bunx ... &` in a bash tool call **die when the shell tool times out**. Needed `setsid ... < /dev/null & disown` to keep them alive across the 120s shell timeout. Wasted a restart cycle on this.
  - **Fix for future**: always start background dev servers with `setsid nohup ... < /dev/null & disown` in one shot.

### INEFFICIENCY
- Screenshot capture + image read for verifying emulator UI: model can't read images. Should have gone straight to `uiautomator dump` + grep of `text=` / `bounds=` from the start.
  - **Fix for future**: verify emulator UI via `adb shell uiautomator dump` text output, not `screencap`.

### INEFFICIENCY
- First verification bundle request returned HTTP 000 because the metro process had died silently (see MISSING_INSTRUCTION). Spent one failed curl round before checking `ps`/log.
  - **Fix for future**: check server `ps` + `curl /status` before requesting a bundle.

### WRONG_BEHAVIOR
- Tapped blind coordinates to dismiss the Expo Go first-launch dev menu; it re-opened the dev menu (Continue button). Correct approach: read bounds from `uiautomator dump` first, tap the real control, use `keyevent 4` (BACK) to dismiss dev menu overlays.
  - **Fix for future**: always parse bounds from uiautomator dump before tapping; BACK closes the dev menu.

## Recommendations

- Nothing to add to AGENTS.md for app code. Consider a small operational note: "Emulator UI verification = uiautomator dump text, never screencap. Background servers need setsid+disown." — optional, low priority.
- The reanimated/worklets x86_64-emulator crash is a known upstream class (hermes#1873); no code change needed. If user repeats this, create a skill: "React Native crash with no JS error on x86_64 Android emulator → suspect reanimated/worklets, isolate with vanilla repro, verify via metro stub."

## Verdict

Audit found 0 repeats from previous sessions, 1 MISSING_INSTRUCTION, 2 INEFFICIENCY, 1 WRONG_BEHAVIOR. No lasting issues; stub is uncommitted and revertable.

# Session 2 — real device still crashes; found the actual fix

## Summary

- User reported the same crash on a real physical device (Samsung S25 Ultra, arm64, Android 16).
- Tried committing the stub workaround → device "still failed".
- User provided the tombstone (logcat `-b crash`). Decisive evidence:
  - **Same signature as emulator**: `memcpy/memmove` → `libhermesvm.so` → `libworklets.so` → Hermes GC frames on `mqt_v_js` (JS thread).
  - Crash occurs on real **arm64** hardware → my session-1 "x86_64 emulator-only, ARM is totally fine" conclusion (based on hermes#1873) was **WRONG**.
  - `libworklets.so` is *in the crash stack* → worklets actually ran → **the stub was never active on the device** (metro config change needs restart + cleared cache; the device loaded a stale bundle).
- Implemented the documented upstream fix: **Worklets Bundle Mode** (babel plugin `bundleMode:true` + `getBundleModeMetroConfig`, disabling babel-preset-expo's auto plugin add). This avoids the Hermes V1 eval path entirely.
- Verified on emulator: real reanimated/worklets intact, no crash, 3+ min stable, full UI + DB schema render.
- Pushed fix; user later squashed dev..HEAD into one commit "fix expo router silent crash bug".

## Findings

### WRONG_BEHAVIOR (over-conclusion from a single issue)
- I generalized hermes#1873 ("x86_64 emulator only, ARM is totally fine") to this crash **without device evidence**, and told the user the app was probably fine on a physical device. The real arm64 device crashed with a byte-identical backtrace.
  - **Fix for future**: don't generalize a single upstream issue's platform claim to your case; get the actual device tombstone before concluding it's environment-specific.

### MISSING_INSTRUCTION (wasted a device test cycle)
- When asking the user to test a `metro.config.js`/babel change on a physical device, I did not tell them to **restart metro with `--clear` first**. Result: device loaded a stale bundle, stub test was invalid, and we burned a full commit/revert cycle on it.
  - **Fix for future**: any config change shipped for device testing must include "restart metro with `--clear`" in the instructions; verify with the bundle that the change is actually live.

### REPEATED_PATTERN (from session 1: stub-the-symptom)
- Went down the metro-stub path twice before landing on the real fix. The stub masks the symptom (it worked on emulator) but is not maintainable and wasted cycles. Bundle Mode is the documented upstream fix and kept reanimated fully functional.
  - **Fix for future**: for crashes in native animation/runtime libs, look for the upstream-documented workaround (like Worklets Bundle Mode) before hand-rolling stubs.

### INEFFICIENCY
- Two device-test round trips (stub commit → "still fail" → revert) were avoidable; the tombstone, which immediately pointed at worklets, should have been requested in round one.

## Recommendations

- Create a skill: **"RN silent native crash (no JS error)"** → get `adb logcat -b crash` / tombstone first; identify the crashing `.so` (`libworklets.so`/`libhermesvm.so` → worklets/reanimated); search upstream docs for documented fix; verify on emulator before shipping to device. Trigger: crash, SIGSEGV, tombstone, no JS error, "silent crash".
- Consider adding to AGENTS.md: "When testing metro/babel config changes on a device, restart metro with `--clear` first."

## Verdict

Audit found 1 repeat from session 1 (stub-the-symptom), 1 WRONG_BEHAVIOR, 1 MISSING_INSTRUCTION, 1 INEFFICIENCY. Root cause is fixed via Worklets Bundle Mode (pushed, squashed, force-pushed).
