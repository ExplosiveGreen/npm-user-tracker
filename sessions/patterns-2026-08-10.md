## Findings

### WRONG_BEHAVIOR — infra I killed that I didn't start
- The environment already had a working emulator on port 5554; my `emulator -avd e2e` start attempts were failing all along (`FATAL` — the `e2e` AVD pointed at a nonexistent `android-35` image, while the SDK only ships `android-36`). I only noticed after `pkill -9 qemu-system` killed the working pre-provisioned emulator. Lesson: check what's already talking to `adb` before starting/killing emulators, and read the emulator log's startup lines before trusting an AVD config.

### REPEATED_PATTERN — pkill self-matching
- `pkill -f nativewind` matched the shell's own command line (`bash -c '... nativewind ...'`), killing the shell that ran it → two 120s tool timeouts. Same class of footgun as broad `kill` patterns. Fix for future: use exact binary/PID scoped kills (e.g. `pgrep -f` then give explicit PIDs, or match the enclosing binary path rather than a keyword that appears in my own command).

### INEFFICIENCY — E2E fell into env-specific Expo Go behavior
- On a fresh-launched Expo Go, Maestro's first switch interaction pops the React Native dev menu over the app (reproducible on this emulator; `adb shell input tap` and "warm" interactions don't). Diagnosed via probes (element tap vs point tap vs warm-up tap). Shipping fix is in the Maestro flows, not app code: tap, dismiss the dev menu if it appears, and repeat until the expected theme label shows. App logic was verified correct independently.

### REPEATED_PATTERN (from 2026-08-09)
- Again the value of inspecting the *running environment* over trusting docs/assumptions: the AVD config, the pre-provisioned emulator, and Maestro's actual tap semantics were all ground truth. Consistent with prior sessions' finding about reading shipped/runtime truth. Already the AGENTS.md default; no change.

## Recommendations

- Consider a small skill or AGENTS.md note: "Before touching emulator/adb infra, run `adb devices` + read the emulator start log" to avoid killing pre-provisioned environment resources.
- Optionally: the `e2e` AVD image path is still wrong-on-disk (`android-35` referenced, `android-36` present); the environment fix I applied (repoint to `android-36`) is not committed anywhere.
