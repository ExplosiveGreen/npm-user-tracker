# Patterns — 2026-08-09

Session: fix dark/light mode consistency + add a two-state theme toggle following Lea Verou's "Dark mode toggles: two states are enough".

## Summary

- Root causes found: `app.json` had `"userInterfaceStyle": "light"` (native locked to light, dark mode unreachable); the root `<Stack/>` used React Navigation's default light theme (unthemed headers/content on web/native); the `Switch` and `Text` in a `<Link>` were unstyled (black/blue text in dark mode); stray per-screen `<StatusBar style="auto"/>`.
- Built the article's model: 3 states under the hood (override `light`/`dark`, or `null` = system), 2 exposed. `lib/theme-provider.tsx` owns it; evaluation of "pin vs. release" happens only at press time, comparing the target against the live OS scheme — exact `prefer()` from the article's demo. Verified the state machine against the demo's 6 steps (all pass).
- Applied scheme via `nativewind`'s `useColorScheme().setColorScheme('system'|'light'|'dark')` (web: html `.dark` class; native: RN `Appearance` override). System signal from RN `useColorScheme()` — stays truthful on web always, and on native while no pin is active.
- New files: `lib/prefs.ts` (web localStorage / native expo-sqlite KV), `lib/theme-provider.tsx`, `components/ui/switch.tsx`, `components/theme-toggle.tsx`, `components/theme-toggle-button.tsx`. Edited: `app/_layout.tsx`, `app/index.tsx`, `app/db/*`, `app.json`.
- Verified: `pnpm typecheck` clean + a `node` state-machine simulation of the toggle logic.

## Findings

### WRONG_BEHAVIOR (guardrail respected)
- expo-router `<Stack>` does **not** accept a `theme` prop even though React Navigation navigators do; TS rejected it. Dropped it and used `screenOptions` (`headerStyle`/`headerTintColor`/`contentStyle`). **Fix for future**: check the installed expo-router prop types before passing React Navigation container props through expo-router wrappers.

### INEFFICIENCY
- Assumed RN's `ColorSchemeName` was `'light' | 'dark' | null`; RN 0.86 types it `'light' | 'dark' | 'unspecified'`, and `expo-status-bar` has no `backgroundColor` prop in this version. Two extra typecheck cycles. **Fix for future**: for a new RN/Expo SDK, diff the installed `.d.ts` for the APIs you plan to use (Appearance, StatusBar) first.

### REPEATED_PATTERN (from 2026-08-06)
- Recurring pattern: correctness came from reading installed `.d.ts`/runtime source (nativewind/css-interop `appearance-observables`, `conditions.js`) rather than docs. This is the same tactic the last session flagged as the efficient path for alpha-tier/under-documented libs — **already in AGENTS.md habits, no change needed**.

### INEFFICIENCY — pre-existing, not caused by this work
- Web bundle is broken **before** any of these changes: `expo-sqlite@57` web worker imports `./wa-sqlite/wa-sqlite.wasm`, which isn't shipped, and Metro's default `assetExts` excludes `wasm`. The user's own running Metro on :8081 shows the same error. So I could not verify visually in a browser; the app appears to run on native. Worth telling the user; not this task's scope.

## Recommendations

- Consider a skill "NativeWind + CSS-var dark mode" capturing: `darkMode:'class'`, `useColorScheme()` from `nativewind` (vs RN) for set vs. read, three-state model stored as override, and the "web always sees the true OS, native pins hide the OS" difference.
- Tell user the web bundle needs `wasm` assetExts handling for `expo-sqlite` if they serve web.
